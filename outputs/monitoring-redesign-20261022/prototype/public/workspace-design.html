AI 工作空间体验复盘与下一版设计建议

日期：2026-10-22。状态：由 V2 代码核查与讨论演进，V4 已同步用户确认的范围、详细设计及独立原型；生产能力仍需按实施阶段开发与真实验收。

V4 范围更新（用户已确认）：遵循当前版本项目范围，只做中文浅色桌面，1440×900 为主，1366×768/1920×1080 检查；不投入移动/平板、深色、听读顺序、完整无障碍及其他范围排除专项。保留基础标签、键盘、焦点和错误状态。纳管对象无 Agent，人工建设原生模板，不做 Zabbix 兼容；AI Agent 运行时保持现状。事件中心移除重复规则配置，证据引用当时规则快照。

用户已确认首版优先级：故障排查与恢复闭环优先，同时兼顾日常巡检和性能优化。这项确认针对产品优先级，不代表整份讨论稿或生产开发已经获批。

用户补充要求：减少手工输入，按“上下文自动带入 → 权威记录读取 → 可复核默认/草案 → 搜索筛选选择 → 必要补充”的顺序设计。静态核查发现及逐环节要求见输入负担排查。事件信息完整或资源常见场景下，首版发起调查应无需必填自由文本；手工描述为可选补充或自定义问题入口，标题自动生成可改。

1. 资源概览的范围纠正

保留当前项目的资源概览，而非用三张资源分类卡替代。现有子标签及顺序为：综合态势、数据库、服务器、网络设备；数据库子标签继续保留引擎筛选。

保留既有统计与联动：按资源去重的统计、风险队列、运行状态分布、采集质量、资源明细与证据，以及按资源类别展示的专业指标、数据库类型/容量趋势、网络配置备份摘要。搜索、子标签、局部筛选、返回位置和权限/不完整数据语义继续有效。四个资源管理菜单与上述子标签是两个不同层级，均不削减。

资源概览中的“查看证据”继续支持无模型阅读；“只读诊断”衔接 AI 工作空间并携带对象、事件、窗口和返回上下文。只整合入口，不因本轮 AI 设计重做资源概览。

依据：frontend/src/app/ui/views/dashboard.ts、dashboard-model.ts、frontend/src/app/i18n/locales/operations-overview.ts。

2. 定位与当前缺口

建议定位：AI 工作空间帮助用户围绕一个具体运维问题，持续收集证据、形成判断、协作决策并验证效果。调查是持续工作的载体，对话是协作方式，证据是判断依据，行动与验证形成可追踪结果。

代码已有调查列表与创建、多资源选择、资源/平台两种 Profile、执行与调查/问题状态分离、持续补充、历史执行、证据与结果版本、根因验证标识、可信案例与行动入口。这些是可复用基础；实际接通、配置和业务可用性仍须另行验证。

当前产品界面存在技术术语、创建字段较多、结果/证据重复、三栏占宽、下一步分散等问题。V2 原型则偏另一方向：静态样例清楚，但“资源诊断/平台诊断”像两套固定功能页，缺少通用发起入口、持续协作、实时进度、统一调查历史和明确下一步，没有充分表达已有机制。

具体依据：

  • frontend/src/app/ui/views/investigations.ts：创建手动调查、Profile 高级筛选、列表/执行协作/证据三栏；1439px 以下证据栏转为弹窗。
  • frontend/src/app/ui/components/investigation-create.ts：标题、目标、资源、时间窗口与 Ops/System；已有按名称多选资源，技术 ID 为高级入口。
  • frontend/src/app/ui/views/investigation-detail.ts：执行/调查/业务问题三类状态、摘要、事实、缺口、下一步及持续补充。
  • frontend/src/app/ui/components/investigation-context.ts：结果版本、事实/假设/反证、根因验证及证据引用。
  • frontend/src/app/ui/components/investigation-operation-context.ts：可信案例、结果整理案例、行动计划及关联事项。
  • apps/db-ops-api/src/investigations/result-schema.ts：证据绑定与结果版本；机器结果不能自行宣称人工/实验验证或恢复。

3. 三条产品路线

方案 收益 代价 结论
对话优先，工具结果进入聊天流 起步容易，接近通用 AI 使用习惯 范围、结论、证据和待办容易埋在长对话里，跨班交接困难 适合轻量咨询，不作为唯一主体
流程看板优先，逐步走排查/审批/执行/验证 责任与操作阶段清楚 排查有分支、反证与反复验证；纯分析任务容易被迫走多余步骤 行动阶段可借鉴，不固定整项调查
持续调查优先，结合对话、证据和任务动作 低门槛发起，长期保留上下文，兼容复杂运维闭环 需要认真设计状态呈现、证据引用与运行反馈 推荐；复用现有 Investigation 基础

按用户已确认的优先级，产品先以故障排查与恢复验证建立代表性闭环，同时兼容巡检、性能优化和变更后核验。几类目标采用不同问题提示与结果结构，不各建一个菜单或独立工作台。

4. 首页：开始工作与继续工作

首页的主要区域是“描述问题 / 选择上下文”的轻量发起区，以及可继续的调查列表。持续使用后，最近/进行中的调查应获得更大空间，不保留巨幅宣传区。

发起区并列支持“选择问题场景”和“自由描述”，不把写提示词作为启动前提。事件/资源进入优先使用上下文路径；从工作空间发起可搜索选择对象和常见问题。关联信息、问题标题和时间窗口自动带入后以摘要呈现，允许局部修改。缺失信息用结构化问题补充，“不清楚”须可选。

示例输入：“订单库从 10 点半开始响应慢，帮我排查。”资源按名称补全；从事件、资源、指标历史或平台异常进入时自动带入已有上下文。建议标题自动生成并可编辑，不强迫先填标题。对象与时间须在启动前清楚确认；有歧义时只问缺失项。

首页“需要你处理”只展示与当前用户相关的补充、审批或验证请求，引用原调查/审批/事件。该区域不复刻告警列表、不建立独立待办状态、不替代事件中心。

调查列表展示：问题名称、主对象、用户可理解的当前进度、最近有效结论或阻塞原因、更新时间；按对象/类型/状态筛选。资源诊断与平台诊断共用列表和详情框架，作为对象类型与模板选择。Ops/System、Run ID 等技术名留在详情。

5. 启动前：上下文确认与能力检查

统一确认卡包含目标、主对象、拟纳入的关联对象、绝对时间窗、证据可用性和执行方式。高级信息默认折叠。

  • 数据准备、资源/工具权限、模型可用性与执行范围分别判断，不能用一个“就绪”掩盖缺口。
  • 无有效样本时，明确提示去绑定模板、测试采集或查看历史；允许有价值的部分分析，但不能输出当前健康/根因结论。
  • 模型不可用时，仍可阅读已经授权的证据；“查看事实”和“启动 AI 分析”分开。
  • 推荐资源来自有来源的关系。纳入前展示理由；推测关联不能冒充已确认依赖，也不自动无限扩大范围。
  • 从故障发生时刻锚定证据窗口；相对时间转成明确时间。历史故障证据与当前状态分开，不自动用当前值替代故障现场。
  • 只读调查和变更操作分开；创建调查不会赋予写操作或审批权限。
  • 预计用量或费用只在有可靠依据时展示，未知就说明未知，不生成看似精确的数字。

资源与平台共用产品交互，不表示混用工具授权。现有资源/平台 Profile 和对象边界继续成立；跨领域关联采用明确的证据引用或关联调查，不默认把所有资源工具交给平台调查。

6. 调查详情：先回答用户最关心的问题

建议采用可折叠的调查导航、主协作区和按需展开的上下文/证据区。常规宽度以主区加辅助区为主，避免三个永久等重栏。窄屏保留当前判断与下一步，不要求用户反复开弹窗才知道结果。

区域 默认呈现 按需展开
固定上下文 目标、对象/数量、时间范围、当前状态 纳入/排除原因、范围与版本变化
当前判断 目前发现、影响边界、证据是否充分 支持证据、反证、替代假设、历史结果对比
下一步 一项优先动作及原因 其他合理路径及其前提
协作过程 用户补充、检查进度、关键发现、结果更新 工具参数、原始回执、诊断技术详情
证据与资源 被引用的关键指标、日志和关系 完整证据包、拓扑、来源、采集/有效时间
行动与验证 行动计划状态、实际效果 预检查、审批版本、执行回执、回退与审计

当前判断与每条结论应能打开对应证据；事实、推断、待验证假设和历史案例明确分开。不展示无校准依据的“根因置信度 96%”。

进度显示真实检查活动，例如“已读取连接指标，正在检查采集日志”，而非伪造百分比或持续转圈。过程呈现可审计的检查摘要，不暴露模型内部推理。长工具输出默认折叠，用户无需在大量 JSON 中找结论。

支持用户自然补充、质疑与纠正，例如“这台服务器不承载订单库”“只看变更后的 20 分钟”“先验证网络，不执行操作”。改变下一轮范围或目标时明确确认，保留之前执行与结果版本；不静默改写已经在运行的任务或历史结论。

7. 状态与下一步

系统保留执行、调查、故障/业务问题三层状态。主界面用一句话讲清“现在怎样、谁该做什么”，详细状态再展开。

场景 用户表述示例 主动作
准备好分析 对象和时间已确认，可以开始只读排查 开始只读分析
正在执行 正在读取连接指标；离开页面后可继续查看 查看进度 / 取消本轮
等待补充 本轮分析已结束，还需要确认连接池上限 补充信息
证据不足 指定时间没有有效样本，暂不能判断根因 补充采集 / 调整窗口
部分完成 已完成两项检查，日志读取失败，已有结果保留 查看缺口 / 针对性重试
等待批准 行动计划已准备，等待指定版本审批 查看计划 / 审批
分析结束 已形成判断，故障恢复尚未验证 继续验证
提交结果未知 正在核对原请求，暂不重复提交 查询原请求
已恢复 复测支持恢复，调查记录可归档 查看验证 / 整理案例

“取消本轮”不等于关闭调查、解除模板或停止正式采集。断线重连应恢复已持久化过程；刷新、离开和重试不能产生额外重复执行。

已结束故障重新出现时，先判断属于原事件复发还是新事件；关联历史调查与案例，保留各自发生窗口，不能把多次事故混成一个无限延长的事实窗口。

8. 行动闭环与持续积累

诊断不应只有一段回答。建议以结构化方式呈现假设及验证方法、建议动作、前提与预期观察，让用户从只读排查自然进入行动。

行动草案可由 AI 辅助生成，但实际执行复用已有行动计划、预检查、不可变版本、人工审批、执行和效果验证机制；不在聊天气泡里放一个绕过计划的“立即修复”。不需要变更的调查可直接形成结论，不强制走全部阶段。

恢复验证不能只看“命令成功”或一个瞬时正常值。按具体问题定义指标、基准、观察窗口及负面影响；反馈“恢复 / 未改善 / 证据不足”。结合触发器恢复证据与必要的人工确认，保持事件、调查、执行各自的责任边界。

输出可交接的一页摘要：问题与影响、时间线、证据支持的结论、未解决疑点、执行动作、效果验证和下一位处理人。团队成员和交接仍受既有权限约束，不因一个分享链接扩大访问。

从有效结果版本整理案例候选，经过脱敏和审核后进入可信运维知识。再次遇到相似问题，展示适用范围、版本差异和反例；历史案例不能作为当前故障已发生或已恢复的事实。采纳/驳回、无效动作与回退记录也有价值，不能只沉淀成功故事。

9. 主动分析与对话的关系

工作空间的主动性体现在：复用现有事件识别值得调查的问题、推荐下一项有依据的检查、运行结束通知用户处理、提示过期证据或验证窗口变化。模型启动受显式策略、去重、冷却和预算约束；打开首页或刷新不触发付费分析。

“对话”继续承载临时咨询、知识问答和 SQL 解释。需要关联真实资源、后台执行、持续证据及处理结果时，可确认范围后转成调查；原对话作为来源引用，工作空间成为后续调查的唯一入口，不复制两套执行会话或结果真相源。

10. 下一版原型的重点

不以增加页面数量为目标，优先用一个完整故事验证体验：

  1. 从数据库风险进入，自动携带资源、告警、故障时间与返回位置。
  2. 展示能力检查：可读取数据库证据，应用连接池设置未知。
  3. 启动只读分析，看真实阶段与关键发现。
  4. 用户补充或否定某个关联，确认下一轮范围。
  5. 基于证据更新判断，保留结果版本差异。
  6. 创建行动草案，在审批/执行入口核对准确版本。
  7. 比较前后观测，发现没有改善时继续排查；恢复时给出验证证据。
  8. 输出交接摘要或整理案例候选。

再补一条平台异常故事，复用同一调查框架，并覆盖缺采集、缺模型、无权限、部分失败、断线重连、提交未知和过期证据。资源概览按现有内容保留，不因原型故事缩减。

优先级：先完成发起/继续、上下文、可读状态、结论与证据、下一步，再强化行动验证、交接和知识积累。主动推荐与更复杂的定期调查应在首条真实业务闭环可靠后建设。

首版完整闭环的验收终点是：能够从真实事件推进到有证据的判断，必要时经行动审批与执行，再通过前后观测判断恢复、未改善或证据不足。仅生成分析报告不能算闭环通过；巡检和性能优化不作为首版同等投入的独立主线。

11. 体验验收建议

  • 从已有事件进入无需重新输入资源与时间；启动前可看见并纠正范围。
  • 首页能快速找到上一项调查、当前阻塞和需要自己处理的动作。
  • 事件信息完整及资源常见场景下，发起前必填自由文本为 0 项；自定义问题不要求再写标题。继续检查支持点选有依据的下一步，标准闭环无需手工输入任何内部 ID 或版本号。
  • 用户不阅读技术日志也能说明：正在检查什么、已知道什么、还缺什么、下一步做什么。
  • 每项结论可追溯到具体对象、时间、来源和证据；反证与证据不足明确可见。
  • 资源/平台调查共享体验与历史检索，但工具权限不相互扩大。
  • 无数据时提示补采集，不输出虚假根因；有部分证据时保留有用的部分结果。
  • 断线、刷新与重试不会重复启动任务；新输入不会静默改写当前执行。
  • 分析、执行与恢复分别判断；动作无效时能返回同一调查继续推进。
  • 窄屏、键盘、长结果、撤权、证据过期均可用，不依赖固定三栏或弹窗嵌套。

以上是拟采用的验收标准，不是本轮已经运行并通过的业务测试。
