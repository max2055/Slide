# Zabbix 模板、监控项与触发器实机探索

研究时间：2026-10-21 晚至 2026-10-22 凌晨（Asia/Shanghai）。
性质：竞品机制研究与 Slide 产品讨论补充，尚未批准为开发合同。

## 结论

用户强调触发器是正确的。Zabbix 模板同时定义“采什么”和“什么情况算问题”，并通过具体主机上的监控项、触发器实例，将采集、历史、问题与恢复联系起来。Slide 的目标应扩充为：

**模板配置 → 资源绑定与参数覆盖 → 正式采集 → 最新/历史数据 → 触发器判断 → 问题事件 → 恢复 → 通知与处理记录。**

建议采用这套领域关系，复用 Slide 现有采集、指标语义和告警服务。模板中的“触发器”应成为与监控项并列的核心页签，统一映射到现有告警规则及事件体系。对于是否直接使用 Zabbix 作为后端，保留独立的架构选择，不能从本次实验推导为已决定引入。

## 环境与证据边界

- 独立 Docker Compose 项目：`slide-zabbix-lab-20261021`。
- 官方 Zabbix Server/Web/Agent2 7.0.21 LTS，PostgreSQL 16.10；镜像固定 digest，详见 compose.yaml（历史附件 `compose.yaml` 未随附） 与 environment.json（历史附件 `environment.json` 未随附）。该版本是本次研究版本，不声称最新补丁版本。
- 本地入口：http://localhost:18080；Sender 只绑定 `127.0.0.1:11051`；独立数据库卷及 Docker 网络，数据库不暴露宿主端口。
- 保留运行供讨论。没有改动 Slide 产品代码、共享配置、业务数据和现有 Multica 任务，没有调用产品 LLM，也没有发送外部通知或执行远程修复命令。
- **真实采集**：Agent2 采集实验容器自身 CPU、内存、文件系统、接口等。最终 158 个监控项，147 个曾有样本，其中 4 个为下述人工场景项，即 143 个非场景项曾有样本。这不代表 158 项全部正常。
- **受控场景数据**：`lab.cpu`、`lab.available`、`lab.heartbeat` 通过真实 Sender 协议注入指定值，验证真实 Zabbix 引擎、存储及事件行为。CPU 95% 是注入的场景值，没有对容器施加真实 CPU 压力；派生项 `lab.cpu.fraction` 执行乘 0.01 的预处理。
- **已实测**：绑定与嵌套继承、参数覆盖、预处理、触发/保持/恢复、去重、依赖抑制、无数据、确认、维护抑制、历史值与图形、单项 Agent 测试、表达式测试。
- **只查看配置/入口**：动作条件、问题/恢复/更新操作、升级步骤、立即执行入口。立即执行已点击，但没有将新增样本与本次手动请求独立关联，不将其列为因果验证通过。
- **未覆盖**：真实消息投递、远程命令、全部采集协议、长期趋势与清理、负载容量、HA、完整安全/权限矩阵。实验时间不足以验证 365 天保留或全部按小时趋势聚合行为。

## 实际模型

实验主机 `Slide Lab Linux` 同时绑定官方 `Linux by Zabbix agent` 与自建 `Slide Lab Service`；后者继承 `Slide Lab Monitoring`。

基础模板包含 4 个监控项、3 个触发器和图形，宏默认高阈值 80、恢复阈值 70。主机把高阈值覆盖为 90，恢复阈值继续继承 70。有效宏界面能同时显示当前值与模板来源，而不是让用户猜测哪层配置生效。

官方 Linux 模板在本版本包含 43 个直接监控项、15 个直接触发器、3 条发现规则、8 个图形及 3 个仪表盘。绑定主机后，自动发现生成额外的文件系统/接口监控项与触发器，故主机总数显著高于直接模板计数。

证据：绑定与宏（历史附件 `host-binding-and-macros.json` 未随附）、官方模板（历史附件 `builtin-linux-reference.json` 未随附）、发现规则与原型（历史附件 `discovery-and-prototypes.json` 未随附）。

## 触发器实测

CPU 场景触发器配置：

```text
问题：last(/Slide Lab Monitoring/lab.cpu) > {$LAB.CPU.HIGH}
恢复：last(/Slide Lab Monitoring/lab.cpu) < {$LAB.CPU.RECOVERY}
依赖：LAB: Upstream unavailable
事件：Single；禁止人工关闭
主机有效阈值：90 / 70
```

### 需要准确借鉴的语义

1. **触发器是有状态的问题判定。** 支持 `last/min/max/avg` 等函数、时间窗、多监控项表达式及宏；不能把“最近一次超过阈值”当作全部机制。本次实测自建场景使用 last；官方 CPU 模板的 `min(...,5m)>阈值` 已查看配置，未另外施压验证五分钟行为。
2. **独立恢复条件用于抑制抖动。** 恢复表达式模式下，问题表达式必须为假，且恢复表达式为真，才生成 OK。95→85→60 的实测体现这一点；不能只看到问题条件为假便立即恢复。
3. **依赖与维护作用不同。** 本次上游依赖阻止新下游问题；维护则保留采集和问题，并标记抑制。依赖不等于已经证明根因，不应把配置依赖直接展示为 AI 根因结论。
4. **确认与恢复独立。** 确认记录有人处理，恢复表示判定状态变化；手动关闭则另受触发器设置约束。UI 要明确展示操作影响。
5. **缺数据需要显式处理。** `last()` 不是采集新鲜度判定；保留的旧值可能继续存在，不能自动解释为采集正常。`nodata()` 是显式无数据规则，执行也存在调度延迟。本次 60 秒配置约 79 秒触发，不能承诺精确第 60 秒报警。
6. **动作与触发器分工。** 触发器定义问题，动作定义哪些事件通知谁、何时升级、恢复或更新时执行什么。默认动作保持禁用，本次没有验证消息到达。
7. **动态对象也需要触发器原型。** 文件系统发现含 7 个监控项原型和 5 个触发器原型，使用 `{#FSNAME}` 生成具体对象规则，并支持不同严重度之间的依赖。

## 数据与交互观察

从“最新数据”可看到值、变化、最近检查、标签，再从同一监控项进入历史。历史支持数值表、图形和最近 500 值等视图，保留时间范围。实测 CPU 场景历史能看到 85、95、85、60 等注入记录及准确时间，图形也显示有效高阈值 90。它提供了判断触发原因的数据上下文。

单项 Agent 测试从真实 `agent:10050` 读取 `system.cpu.util[,idle]`，返回 `89.980329`，完成数值类型转换。测试对话框将读取、输入值、前值、预处理结果及错误放在一起，能解释失败发生在哪一步；测试与正式“立即执行”是两个入口。

官方模板也存在环境不匹配：本容器中 10 项不支持，包含包信息读取和部分虚拟接口速率文件。错误作为具体监控项状态保留；另有 1 项尚无历史样本，不能由其他项有值推断它正常。证据见 final-item-health.json（历史附件 `final-item-health.json` 未随附）。这要求 Slide 在批量测试时显示成功、失败、不支持、未采样的数量与详情。

Zabbix 的机制清楚，但本次窄屏（约 663px）下嵌套对话框存在横向遮挡，测试按钮一度处于可视区外；键盘仍可触发。1440×1000 桌面对照下可完整查看主要配置。两种宽度的观察不能推导为全面响应式验收。Slide 可改进为单层抽屉或独立详情页、固定操作区、折叠高级项及条件摘要，避免照搬多层弹窗。

## Slide 推荐实现方向

### 三种路径

| 路径 | 收益 | 代价与适用条件 |
|---|---|---|
| **Slide 原生完善，采用上述领域关系（推荐）** | 保留三类资源、权限、版本、指标语义与 AI 数据口径；工作台一致 | 需要完善模板实例化、表达式/依赖、历史查询和事件闭环；现有服务须核实接线，不能只改页面 |
| Zabbix 作为可选监控后端，Slide 提供工作台 | 可复用成熟模板、采集、触发器和历史能力 | 增加运维依赖、身份/权限映射、版本兼容和配置归属；须定义谁是唯一配置来源 |
| 只整理当前配置页与术语 | 较快改善理解与入口 | 满足不了用户已明确的可管理监控项、模板组合、触发器与历史闭环要求，可作为临时改善 |

### 用户可见的工作台

- **监控模板**：概览、监控项、触发器、发现规则、图形、参数、关联资源、版本。显示数量及来源；内置可复制，自定义可编辑、测试、发布。
- **资源详情**：概览、监控项、触发器、历史图形、监控配置。绑定多个模板后可查看实际生效配置、覆盖来源与冲突；恢复继承是明确操作。
- **最新数据**：统一筛选资源/监控项/标签/状态；当前采集错误与最近成功值分别展示；一键进入历史数值/图形。
- **问题中心**：显示严重度、开始/恢复时间、持续时间、确认、抑制与原因；详情包含判定表达式、有效参数、命中数据和时间线，链接回具体监控项历史。
- **通知策略**：在问题/恢复/更新事件上配置渠道、接收人、升级和维护抑制；不把通知设置塞入每条触发器的基本编辑区。

### 触发器编辑体验

默认用结构化编辑：监控项 → 统计方式与窗口 → 比较条件 → 阈值/参数 → 严重度 → 恢复条件；高级模式支持经过校验的表达式和多条件组合。保存前把规则翻译成中文摘要，例如“过去 5 分钟 CPU 最小值高于 90% 时产生问题，回落低于 70% 后恢复”。缺数据处理、最低覆盖率、规则启停和依赖关系应可解释。

区分三类测试：

1. **测试采集**：验证当前凭据、读取与预处理，逐监控项返回值/单位/耗时/错误；测试样本保持隔离。
2. **测试表达式**：允许填边界值，显示每个条件和整体结果，不创建真实问题。
3. **历史回放（增强）**：选真实资源与时间窗，显示触发/恢复区间及缺测原因，附模拟结果标记，不发送通知。Zabbix 本次实际查看的表达式测试是人工填值，历史回放属于 Slide 建议能力，不能描述为本次已验证的 Zabbix 功能。

### 与现有代码衔接

Slide 已有指标阈值、持续时间、恢复阈值/时长、质量与单位校验、缺失输入 unknown 的评估基础，见 `apps/db-ops-api/src/metrics/consumers/evaluation.ts`。另有 `alerts/compiled-rule.ts`、`alert-event-service.ts`、`alert-silence-service.ts` 与 `notification-service.ts` 等服务。

这些是可复用基础，不代表已存在 Zabbix 等价的完整表达式、模板继承与触发器原型能力。需统一现有入口及运行路径，形成“模板触发器定义 → 资源有效规则 → 评估 → 事件 → 通知”的同一条链，避免新增另一套互不相通的告警引擎。该判断属于源码分析，本轮没有对 Slide 告警端到端重新验收。

尤其应将三个维度分别保存：业务问题状态（正常/问题）、评估质量（有效/未知及原因）、处理状态（确认/抑制等）。采集失效不能把未恢复的问题自动抹成正常；旧问题也不能掩盖当前评估已缺乏数据。

此前报告指出的历史身份、停用/解绑后历史访问、相对当前时间的新鲜度过滤与 1000 源点读取上限仍需纳入设计；这些问题会同时影响图形和触发器历史解释，详见 [此前讨论稿](../monitoring-model-discussion-20261021/ANALYSIS.md)。

### 分阶段交付与可验证标准

1. **第一条完整闭环**：监控模板包含监控项及触发器；资源关联、参数覆盖、测试、启用；正式数据进入最新值/历史；基础阈值与独立恢复产生可追溯问题/恢复事件。三类资源各选一个真实代表对象验收。触发器应进入首批闭环。
2. **组合与降噪**：多模板、嵌套继承、冲突解释、批量变更/版本影响；条件组合、依赖、维护、确认与通知路由。实现次序可按现有接口成熟度细分，但领域模型先保留关联身份和来源。
3. **动态与长期能力**：发现规则、监控项/触发器原型、长期趋势、历史回放及诊断联动。正常 24h 历史查询正确性应在第一批解决，不能后移至长期趋势阶段。

最终验收至少复用本次的 95→85→60、主机覆盖、上游依赖、无数据、确认仍未恢复、维护抑制等案例，并增加断线重启、重复评估、模板升级及权限负例，验证不重复建事件、不误恢复、证据可回看。通知真实到达须单独验收；AI 分析应引用同一指标、维度、时间窗和规则版本的数据依据。
