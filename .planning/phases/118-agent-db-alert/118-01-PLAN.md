## Plan 118-01: 告警系统 Bug 修复

### Objective
修复 3 个告警系统 bug：可用性告警误报、QPS 阈值绕过、API metric_name 为 null

### Bug 1: _availability 误报 — 可用性告警每 15min 触发

**Root Cause**: `alert-evaluator.ts` 中 stale 检测阈值固定 5 分钟，但 monitor-collector 采集间隔为心跳 10s + 定时采集 5min，某些指标采集间隔 > 5min 导致健康实例也被标记为 stale

**Fix**:
- `alert-evaluator.ts`: 将 stale 阈值从固定 5min 改为可配置（默认 10min）
- 或者基于实例实际的 `last_health_check_at` 来判断，而不是 metrics dated_at
- 可用性判断逻辑：仅当 `health_status='critical'` 且 metrics 过期 > 10min 才创建可用性告警

### Bug 2: QPS 阈值绕过 — 规则阈值 30000 但仍触发

**Root Cause**: `evaluateAllRules()` 中 `resolveDynamicThreshold()` 可能从 `metric_definitions.threshold_template` 或 `metric_templates.macro_defaults` 返回了更低的阈值

**Fix**:
- `alert-evaluator.ts`: 调查 `resolveDynamicThreshold()` 和 `resolveMacrosForRule()` 对 Oracle QPS 的解析结果
- 确保 dynamic threshold 不会覆盖 enabled 规则的显式阈值，除非规则本身配置了 `threshold_template`
- 修复阈值优先级：规则显式 threshold > metric_definition.threshold_template > metric_template.macro_defaults

### Bug 3: API metric_name 为 null

**Root Cause**: 前端 API 可能在不同路径返回告警数据，alertDatabaseService.getAlerts() 返回的行到 JSON 映射丢失了 `metric_name` 字段

**Fix**:
- 检查 `alert-database-service.ts` 中 getAlerts 的 SELECT 和 row 映射
- 确保 `metric_name` 包含在查询结果和序列化输出中

### Tasks
1. Fix stale metrics threshold (change 5min → 10min, add health_status check)
2. Fix resolveDynamicThreshold() overriding explicit rule thresholds
3. Fix API metric_name null in alert response
4. Clean up existing false alerts, restart server, verify
