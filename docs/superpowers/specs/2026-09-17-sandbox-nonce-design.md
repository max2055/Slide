## 方案比较

1. **推荐：共享 MySQL 原子 nonce 认领。** 复用现有持久化基础设施；唯一键处理多副本竞争，InnoDB 提交后才允许执行。代价是 controller 新增数据库依赖和最小权限凭据。
2. Redis SET NX：延迟较低，但需新增生产服务，并处理淘汰、持久化丢失及异步故障转移，不能只靠 TTL 宣称重启安全。
3. 稳定 execution id：适合结果重取，但需要客户端协议、持久执行状态与恢复对账，范围明显更大。

## 推荐方案执行契约

目标：同一有效签名请求在多个 controller 及其重启后最多进入执行路径一次。保留现有 HMAC timestamp/nonce/body 格式及 ±30 秒窗口，不变更客户端协议。非目标：保证每个请求一定执行成功、对已执行结果提供重取、改变全局并发限额、部署生产。

- 增加共享 nonce 表，主键为固定认证域和 nonce；不存 secret、签名或 body。所有使用同一 secret 的 controller 必须访问同一权威写库与认证域。
- 先校验格式、签名，再向共享存储认领。窗口以权威数据库时间复核，避免副本时钟差异导致记录被提前清理。重复唯一键拒绝；无论响应丢失、进程崩溃还是后续作业失败，都不释放已认领记录。
- 认领使用原子插入，提交成功后才可创建 workspace 或运行命令。数据库错误、超时、提交结果不明均 fail closed，HTTP 503；重复、篡改和过期为 401。status、jobs、network-scans 所有现有签名入口统一使用异步鉴权。
- 记录保留到签名的最后合法时刻之后，并至少覆盖原有 60 秒 nonce 保留期；清理使用数据库时间与严格小于比较，分批删除，TTL 清理失败只影响容量、不允许绕过鉴权。不存在过期记录原地覆盖竞争。
- 持久性要求 InnoDB 提交刷盘；不支持把可能丢失已确认事务的异步副本直接升主并立即继续接收请求。数据库回滚、快照恢复或去重数据丢失时，必须停流至少覆盖完整 freshness 窗口并留时钟余量，或轮换 secret 后再恢复。
- 表通过幂等迁移创建。配置缺失时启动失败，存储暂时不可用时保持拒绝执行；恢复连接后仅新独立请求可执行，不做内存降级。Compose 增加 controller 到数据库的受控连接及配置说明。

## 验收与停止条件

1. focused tests：格式、HMAC 篡改、过去/未来窗口边界、独立 nonce、重复 nonce、存储异常及提交不明。
2. 隔离 MySQL 与两个独立 controller 进程：同一签名并发与顺序提交，无害测试执行器计数合计最多一次；重启 controller 后再次提交仍拒绝。测试执行器与生产 Docker socket 隔离。
3. 数据库断连/恢复、过期清理、数据库正常重启后的记录保留测试；不触碰当前运行服务和真实生产容器。
4. 最终运行 controller 完整测试和 typecheck，以及受影响的客户端兼容检查与部署配置检查。无关失败记录，不顺手整改。
