# System-Global Agent Sandbox Design

## Goal

Add a system-global switch for Agent-generated arbitrary code execution. The switch is disabled by default. When enabled, Shell, Python, and Node execution must use `SandboxClient.execute()` and must fail closed when sandbox execution is unavailable. SQL and other structured tools retain their existing controlled executors.

## Scope

This design covers code generated by an Agent and submitted through a new, dedicated `execute_code` tool. It does not redirect SQL, database maintenance, SSH workflows, or other structured platform tools into the sandbox. It does not create or retain a host execution fallback.

Supported runtimes are limited to runtime identifiers configured and reported by Sandbox Controller. The initial implementation exposes only configured Shell, Python, and Node runtimes; an unavailable runtime is rejected before execution.

## Architecture

The feature uses a dedicated Agent tool backed by a small code execution service. This boundary ensures arbitrary code has one production entry point and prevents unrelated tools with an `execute` security effect from being intercepted.

The execution path is:

```text
Agent
  -> execute_code tool
  -> actor-bound tool policy and per-execution approval
  -> AgentCodeExecutionService
  -> authoritative global setting check
  -> SandboxClient.execute()
  -> Sandbox Controller
  -> rootless isolated container
```

`AgentCodeExecutionService` is the mandatory application boundary for Agent code execution. It never calls a process API, shell, language runtime, SSH client, or host executor. The only enabled execution dependency is `SandboxClient.execute()`.

## Global Configuration

The persistent setting key is `agent_sandbox_enabled` in `system_config`. Absence, malformed values, read failures, and migration/upgrade states all resolve to disabled. The database migration installs an explicit false value without overwriting an existing valid value.

An administrator-facing API is added under the existing Agent security routes:

- `GET /api/agent/security/sandbox/config`
- `PUT /api/agent/security/sandbox/config`

Both endpoints require authenticated system-administrator authorization. Updates are validated as strict booleans and recorded in the security audit log with actor, previous value, new value, timestamp, and outcome.

Enabling performs a readiness check using `SandboxClient.status()`. The update is rejected unless the controller is configured, reachable, healthy, reports rootless operation, and exposes at least one permitted runtime. Disabling does not depend on controller availability and takes effect immediately.

Execution reads authoritative server-side configuration for every request. This avoids stale enabled state after an emergency disable and keeps fail-closed behavior simple. No client-provided value can override the setting.

## Agent Tool

The `execute_code` tool accepts:

- `runtime`: a strict allowlisted identifier for Shell, Python, or Node;
- `code`: source text subject to the controller input limit;
- optional bounded supporting files;
- optional timeout within controller limits.

The public tool schema does not expose arbitrary environment variables, image names, container options, mounts, networks, user IDs, capabilities, or Docker arguments. The backend maps each runtime identifier to controller-owned, digest-pinned image configuration.

The tool is registered in the normal actor-bound tool registry so existing permissions, approval workflow, policy enforcement, and audit infrastructure apply. Its security metadata declares an `execute` effect, no network, no credentials, and mandatory approval for every invocation.

When the global setting is disabled, the tool returns a deterministic `SANDBOX_DISABLED` denial. It performs no controller request and no local execution. Keeping the tool registered with a deterministic denial preserves audit visibility and avoids tool-list cache inconsistencies.

## Execution and Data Boundaries

The service constructs a bounded sandbox request and calls `SandboxClient.execute()` with an abort deadline. It passes only the requested source, permitted supporting files, runtime mapping, and bounded timeout. It does not inherit the backend process environment.

Database passwords, JWT secrets, LLM API keys, Sandbox Controller authentication secrets, credentials, and connection strings are never copied into job files, arguments, or environment variables. Sandbox Controller retains its existing HMAC request authentication, nonce replay protection, resource limits, output limits, cleanup, network isolation, read-only root filesystem, dropped capabilities, and non-root identity.

The result is normalized into the Agent tool result contract. Standard output and standard error remain bounded by controller limits. Container identifiers, image internals, HMAC material, and backend stack traces are not returned to the Agent.

## Failure Handling

All uncertain states deny execution:

- disabled, absent, invalid, or unreadable configuration -> `SANDBOX_DISABLED` or `SANDBOX_CONFIG_UNAVAILABLE`;
- controller not configured or unreachable -> `SANDBOX_UNAVAILABLE`;
- unsupported runtime -> `SANDBOX_RUNTIME_UNAVAILABLE`;
- approval denied or missing -> existing approval denial;
- timeout -> `SANDBOX_TIMEOUT`;
- controller authentication, protocol, or execution failure -> normalized `SANDBOX_EXECUTION_FAILED`.

None of these paths invokes a host runtime or another executor. Errors are auditable and provide stable codes without exposing secrets or internal transport details.

## User Interface

The existing Agent security settings/status area gains a system-level sandbox toggle. It uses the project's shared button, form, dialog, badge, and toast components and design tokens.

The toggle displays disabled, enabled, saving, readiness-check failure, and authorization failure states. Enabling requires a confirmation dialog explaining that Agent Shell/Python/Node execution will become available subject to per-run approval. Disabling is always available to an authorized administrator and updates the visible state only after the API succeeds.

The UI is an administrative control only. Backend authorization and the authoritative database setting remain the security boundary.

## Auditability

Configuration reads do not require individual audit records. Every configuration mutation records success or failure. Every `execute_code` attempt flows through the existing tool policy/audit path and records actor, runtime, decision, approval reference, timing, normalized outcome, and bounded metadata. Source code and raw output are excluded from security audit records to avoid persisting secrets; existing redaction rules apply to diagnostic logs.

## Testing

Backend unit and route tests verify:

- absent configuration defaults to disabled;
- only system administrators can read or mutate the setting;
- enabling requires a healthy rootless controller and permitted runtime;
- disabling succeeds while the controller is down;
- disabled execution never calls `SandboxClient.execute()`;
- enabled execution calls `SandboxClient.execute()` exactly once;
- controller errors, timeouts, malformed responses, and setting read failures fail closed;
- runtime and input validation reject unsupported or oversized requests;
- no host process API or alternate executor is reachable from the service;
- policy metadata requires approval, no network, and no credentials;
- configuration changes and executions produce expected audit events;
- SQL and existing structured tools retain their current executors.

Frontend tests verify administrator visibility, strict boolean property binding, confirmation behavior, loading/error states, and immediate display of successful enable/disable changes.

Integration and qualification tests execute a harmless program through the real controller, verify disabled denial, verify enabled sandbox execution, verify network isolation and resource constraints, and prove controller outage does not cause host fallback.

## Rollout and Compatibility

The migration and application both default the feature to disabled. Deployment therefore introduces no new code execution capability until an administrator explicitly enables it after readiness validation. Existing SQL jobs and tools are unchanged. Emergency response consists of setting the switch to disabled; because execution reads authoritative state per request, subsequent attempts are denied immediately.

## Acceptance Criteria

The feature is complete only when all of the following hold:

1. A system administrator can inspect, enable, and disable the global setting.
2. A non-administrator cannot inspect or mutate it.
3. Upgraded and fresh systems begin disabled.
4. Disabled code execution performs no sandbox or host execution.
5. Enabled Shell/Python/Node execution uses only `SandboxClient.execute()`.
6. Every execution requires approval and is audited.
7. Sandbox unavailability and all ambiguous states fail closed without host fallback.
8. SQL and other structured executors remain behaviorally unchanged.
9. Backend, frontend, integration, and sandbox qualification tests pass.
