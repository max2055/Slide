### R2. Worker：DB fencing 有效，外部操作不会自动受其保护

[worker-runtime.ts:113](/Users/max/Coding/40-Slide-main-runtime/apps/db-ops-api/src/workflows/worker-runtime.ts:113) 的 markLeaseLost 只改变标志和 heartbeat；第 144 行等待的 handler 不接收 signal。探针中 A 续租失败，lease 过期后 B claim 同一 job 并完成，然后 A 才产生副作用并返回 retry；DB complete 只由 B 调用，说明 DB fencing 与 handler 副作用确实是两层问题。

实际有副作用的链在 [server.ts:5518](/Users/max/Coding/40-Slide-main-runtime/apps/db-ops-api/server.ts:5518)：notification.deliver 记录 started 后发送通知；[notification-service.ts:174](/Users/max/Coding/40-Slide-main-runtime/apps/db-ops-api/src/notification-service.ts:174) 先发送，再记录 sent。report.notify 第 5537 行也存在外部发送。它们没有将 fencing token 传给接收端；已有 scheduler 去重、delivery attempt 和 report occurrence 记录，不能据此认定所有业务都已经 exactly-once，也不能说项目完全没有业务幂等设计。

修复验收需要两层：lease 丢失后协作取消、停止后续操作；对于已经发出的外部操作，用接收端幂等键/可查询结果/业务状态机处理不确定结果。只有本地唯一约束，仍不能原子覆盖“外部已发送但本地未记成功”的崩溃窗口；SMTP 等不支持幂等键的通道应明确可保证的语义。

### R4. SSH：校验确实可选，但不要误报“私钥泄漏”

[ssh-host-key.ts:38](/Users/max/Coding/40-Slide-main-runtime/apps/db-ops-api/src/security/ssh-host-key.ts:38) 对空 fingerprint 返回 undefined；[config-backup-service.ts:326](/Users/max/Coding/40-Slide-main-runtime/apps/db-ops-api/src/network-devices/config-backup-service.ts:326) 因此不设置 hostVerifier。ssh2 自带 README 明确默认行为是未设置 hostVerifier 时 auto-accept。现有 `ssh-host-key.test.ts:26` 也明确断言允许省略 fingerprint。这不是新回归，而是现有兼容策略。

相同 optional helper 还用于 ssh-session-pool.ts:232 和 server-database-service.ts:438。生产环境也没有在这些位置额外强制 pin。

密码认证时，伪服务器可获得发给它的密码；公钥认证向服务器提供公钥和签名，不会把私钥发送出去，但仍存在对端身份不可信、读取伪造结果等风险。实际风险取决于是否配置 fingerprint、认证方式和攻击者是否能控制网络路径。本次未统计生产配置，也未实施 MITM。

建议先提供受信任渠道核验/显式确认 fingerprint 的录入路径，再迁移生产连接到强制 pin；TOFU 的首次确认不能被描述为天然安全。

### R6. Approval consume 顺序

[policy.ts:204](/Users/max/Coding/40-Slide-main-runtime/apps/db-ops-api/src/tools/policy.ts:204) 在 agent policy、decideToolPolicy 和 decision audit 前调用 consume。探针记录顺序 `consume → audit-failed`，结果 AUDIT_UNAVAILABLE，handler 未执行。真实 consume 服务会将 once 标记 consumed，高风险强制 once，因而这里确实可能消耗审批机会。

建议先完成静态权限、scope 和 policy 判定，将 consume 的原子校验尽可能靠近 handler，并以执行意图/审计记录协调提交。不要只增加一次“检查审计可用”：检查通过后存储仍可能失败，必须设计清楚 consume 后失败的恢复语义。

### R7. 已批准 SQL 的审计不是 durable 成功条件
