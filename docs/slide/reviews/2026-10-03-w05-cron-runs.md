## 契约与兼容决定

新业务运行状态：`queued → running → success | partial | failed | unknown | cancelled`。工具仍接受 `failure`，持久化业务状态映射为 `failed`；旧日志 `error/timeout/partial/success` 保留。新日志 `run_id` 关联业务运行；历史 NULL 不追溯结果，页面标记“旧成功（仅 runner 结束）”。

`POST /api/cron/jobs/:id/run` 返回 `202 { runId, jobId, status, message }`。`Idempotency-Key` 按主体、任务和参数摘要绑定，重发仅返回原运行；同键不同参数拒绝。当前不接受额外执行参数。run 和 `workflow_jobs` 调度意图在同一 MySQL 事务中创建；HTTP 无需等待模型。

`GET /api/cron/jobs/:id/runs/:runId` 查询本次结果，先核对当前任务/目标权限，再核对任务与运行匹配。`GET /api/cron/jobs/:id/runs?requestKey=...` 只查当前主体原请求，用于响应丢失后的恢复，不触发新执行。

`queuedAt`、`startedAt`、`runnerFinishedAt`、`completedAt` 分离。完成工具使用 AsyncLocalStorage 绑定当前 runId、schema 快照、取消信号及保存回调；持久化成功才返回 saved。相同完成幂等、不同完成冲突。最终普通文本或看似 JSON 的文本均不算业务完成。runner 结束、失败或恢复不会覆盖已保存 failure/partial。标准 JSON Schema 和历史字段映射均被实际校验；手动/定时读取都带 output_schema，已接受请求使用快照。

typed handler 使用同一运行 ID 和原 worker 取消/fencing context，返回显式业务证据。容量结果以实际落库结果统计；清理错误保留为 failure；无返回证据为 unknown。报表状态指报表已持久化，通知 dispatch 状态仅指调度步骤完成，后续通知交付仍由其独立记录跟踪。原 `JobRegistry.execute` void 接口保留，Cron 通过 `executeWithResult` 读取业务结果。

同任务由内存守卫与 MySQL GET_LOCK 互斥，旧 provider/tool 未 settle 时保留锁；重叠运行取消并注明 CRON_JOB_BUSY。启动恢复在 dispatcher 启动前完成，queued 意图继续，已 started 且未正常结束的运行无完成证据时转 unknown，不自动重跑或再次计费。

页面为每个运行分别管理请求 AbortController 和轮询 timer。缓存只保存当前用户的请求/运行标识及状态，不保存结果或 Token。离线显示“状态待确认”，丢失 POST 响应后只查询原请求；显式再次提交复用未确认请求的键。离开页面取消请求与所有轮询；刷新从原 run 恢复，两个任务互不影响。

## 迁移与回滚

新增 `106_cron_runs.sql`：独立业务运行表、旧日志关联列/状态扩展，以及固定 native handler 的输出契约。所有旧记录保留。先应用迁移再部署后台与新前端；旧客户端对 202 的处理不兼容，必须随此发布同步升级，不提供“已完成”的伪兼容响应。

回滚前停止 HTTP/定时新触发，排空可以完成的运行；保留无法确认的 run/intent/日志与新列，不删除状态、不将 unknown 重新排队。然后停止新 dispatcher 并回滚应用；旧程序不会处理 cron.execute 类型，未排空意图必须保持停用并供人工核对。native 输出契约与状态协议随应用一起升级/回滚，不自行反向修改历史业务结果。
