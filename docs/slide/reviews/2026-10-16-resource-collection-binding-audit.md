# 纳管对象与采集包绑定：实测与流程审计

日期：2026-10-16；环境：本机 Slide；范围：绑定有效性、真实试配、状态显示及配置入口。未实施页面重构、批量绑定或源码修复。

## 结论

绑定记录可以保存，采集包可以在真实资源上执行，但当前普通配置流程没有完成“发布绑定 → 调度执行 → 正式数据源接管 → 页面可见”的闭环。不能把“已应用”或“采集成功”当作用户已经能看到正式指标。

本轮通过浏览器给 mysql3306 绑定 mysql-basic@2.0.0，预检、只读试采及发布成功；短时启用新版调度后，连续 4 轮采集成功，产生 4 个 Raw 和 4 个 Normalized 样本。绑定发布版本和应用版本均为 1。列表刷新后依然显示运行时长“暂无有效值”、采集状态“部分缺失”。数据库大小仍为“未配置”，因为所选适配版本没有容量能力。

已有服务器绑定也连续采集成功 4 轮，但正式发布表和数据源切换登记仍均为 0。因此这些是调度执行落库证据，**不是正式消费者已经接受这些值的证据**。

## 确认的问题

### 1. 发布、调度、正式读取三个环节脱节（高优先级）

`metric-configuration.ts` 的操作到 policy publish 为止；`policy/service.ts` 保存绑定并置为等待应用。调度器受 `METRICS_V2_COLLECTION_ENABLED` 控制，默认关闭；发布页没有显示这一全局阻塞原因。

打开调度之后，`scheduler/store.ts` 可以把绑定标为 applied 并写 Raw/Normalized。正式查询使用 `rollout/formal-store.ts`，却要求有 publication，以及 read_mode=v2、published/applied 一致的 rollout 登记。当前没有这些记录，所以返回空序列。

后端具备 shadow/gate/cutover/confirm 接口，但普通配置页面没有接入。正式切换要求影子对照门禁和更高 revision；这不是“刷新一下”等待几轮就会自动完成的步骤。现有 portfolio 推荐还不覆盖 MySQL 9.6，不能直接假定其可替用户补完。

**修复验收**：从用户正常配置入口出发，能够明确看到所有阻塞，按真实门禁完成接管并得到正式查询值；门禁未通过时必须明确显示“尚未启用正式指标”，不能用“已应用”暗示整体成功。不应删除数据源隔离和影子门禁来掩盖缺口。

### 2. 停用状态存在两套含义（高优先级）

服务器资产记录的自动采集为停用，但新版绑定为启用，开启新版调度后实际执行了 SSH 采集。现有新版 access/scheduler 路径没有把资产的 collection_enabled 作为统一的停用条件。

这可能有历史兼容背景，但用户面对的是同一台资源，无法理解“已暂停自动采集”却仍被另一条链路采集。不能静默把旧字段改成启用解决。

**修复验收**：定义并展示统一的有效采集状态及开关优先级；暂停后相关调度和在途处理行为明确、可验证。迁移期间也应说明当前由哪套来源负责。

### 3. “未配置”混用了对象绑定状态与指标覆盖状态

`MetricConsumerService.query()` 对没有模板的某一指标返回 not_configured；`collectionState()` 又根据列表核心指标聚合整个资源状态。

- linux-basic 只包含 uptime/load，列表核心列却是文件系统容量和网络字节速率。于是已绑定、甚至采集成功的服务器仍会显示“未配置”。
- mysql-basic@2.0.0 只有运行时长，不含容量。数据库大小显示“未配置”容易诱使用户反复绑定；当前适配包根本不能提供此项。
- “应用成功”“采集成功”“正式数据可用”“指标是否覆盖”没有独立呈现。

**修复验收**：对象绑定状态单独计算；单项缺少模板显示“当前采集包未覆盖”，版本不支持则说明“不支持”及原因；正式源未启用与采集失败、等待首个样本分开。

### 4. 首次推荐没有按真实兼容性选择

组件初始默认采用同 resource_type 的第一个包，不按引擎和版本选择。本次 MySQL 9.6 默认得到适用 5.7/8.0/8.4 的旧包；未绑定时选项还列出 PostgreSQL、Oracle、达梦。

选择适配版本后试采能够成功，因此问题不应笼统归因于连接失败。

**修复验收**：按资源类型、引擎、版本和能力推荐；不兼容包明确禁用并解释。包卡片展示覆盖指标，尤其说明列表核心指标的覆盖缺口，避免仅看“基础采集”误选。

### 5. 两个编辑入口确实重复，但数据没有重复维护

详情中的采集配置和设置中的资源采集策略都使用同一个 `<metric-configuration>`、同一组 API 和同一条绑定记录。本轮在详情发布后，设置中读到同版本，未发现两个配置源。

重复在信息架构：用户需要先判断应去哪个入口，而设置中还要重新选资源；详情和设置均暴露“继承、覆盖、策略组标识、预检、试采、发布”等完整管理表单。当前普通资源编辑没有采集包选择。

另有清晰度问题：加载期间先显示“未绑定”；发布后需要手动重新加载观察应用状态；策略组缺少可选列表，只能高级输入标识；部分错误只给通用提示。

## 流程建议（待讨论，未实施）

建议采用用户提出的方向：**资源编辑是单对象配置主入口，详情展示状态与证据，设置管理全局模板和策略。**

| 位置 | 建议职责 |
|---|---|
| 新增／编辑资源 | 基本连接信息；“监控与采集”分区：开关、兼容模板推荐、周期、覆盖摘要；高级覆盖折叠 |
| 资源详情 | 绑定模板及版本、有效开关、阻塞原因、最近采集、正式数据状态；“编辑采集配置”打开同一个编辑器 |
| 设置 → 指标与采集 | 指标定义、全局采集包及版本、策略组、变更审计；需要统一运维视图时提供资源策略列表并跳转共享编辑器 |
| 资源列表 | 可理解的绑定／运行状态、明确的缺口说明；未来提供选择多资源后的批量绑定入口 |

普通用户看到的步骤可以归并为“选择兼容模板 → 检查并启用”。预检、试采和版本发布可以编排在同一流程内，但必须保留影响摘要、明确失败步骤及重试能力，涉及正式接管仍执行必要门禁。保存连接信息与启用采集是不同副作用，应明确分别成功还是失败，不能用一个笼统“保存成功”覆盖部分失败。

另外两个可选方向：保留现有双入口但统一跳转，改动较小，不过仍要解释入口职责；全部集中在全局设置，便于平台管理员，却增加逐对象配置的跳转成本，不建议作为常用路径。

### 后续批量绑定

应在单资源闭环修复后推进。按资源类型／引擎／版本分组推荐兼容模板；预览当前 → 目标差异、覆盖范围及读取成本；逐对象预检、试采与发布；展示成功、跳过、不支持和失败原因，支持只重试失败项。不能把混合资源全部套用同一包，也不能覆盖用户已有配置却不提示。大批量操作应有受控并发和进度，不能只提示“批量成功”。

## 建议实施顺序

1. 先修复单资源的发布／调度／正式源闭环，同时统一开关及状态含义。这些是功能问题，不能仅靠移动入口解决。
2. 再实现兼容推荐及资源编辑的共享配置入口，详情改为状态摘要，设置保留全局治理。
3. 最后实现批量配置，在同一套能力判断和执行流程上扩展。
