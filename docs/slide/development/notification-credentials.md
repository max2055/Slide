# 通知渠道凭据保存与升级

通知渠道将整段 Webhook URL（包括任意路径和查询参数）视为凭据，使用现有 AES-256-GCM v2 信封保存在 config.webhook_url_encrypted。发送时解密，再执行原有 HTTPS、主机白名单、DNS 地址策略及固定连接地址校验；损坏的密文不会回退到旧明文地址。

启动流程在 schema ledger 完成后、注册 API 和启动 worker 前执行通知凭据数据升级。不修改已有 SQL 迁移或 schema。每批最多 100 行，使用同一连接和行锁完成读写；加密历史明文并清理不属于渠道类型的字段，保留现有密文、启用状态、投递起点及创建/更新时间。重复启动不重新加密。某批失败则回滚该批、以固定错误码阻止启动；已完成批次可在下次启动继续处理，不自动重放结果未知的写请求。升级需原加密密钥；不生成明文快照。

升级期间应停止旧版本写入者，重启所有使用新版本的 API/worker 后生效。升级不改变既有备份文件，恢复历史备份后仍需通过新版本启动升级。回退旧版本前需评估其不支持加密 URL 的发送路径，不能通过解密数据库来降级。

配置列表响应只暴露适用的非敏感字段、hasWebhook 和 hasCredential 状态；旧明文记录可返回不含用户信息、路径和查询参数的 endpoint，密文记录无需解密回显。客户端不能提交 *_encrypted 字段或其 encrypted 变体。未知及不适用字段不持久化，不作为替代凭据入口。

同类型配置编辑保留省略的字段与凭据；显式空串或 null 清除对应凭据。切换渠道类型从新配置构造，不保留旧类型密文；只改类型而不提供配置会清空旧配置，发送前继续按新类型校验。仅启停或改名不替换配置。清除邮件必需凭据后发送会返回配置无效；首次创建或切换为邮件仍需提供完整邮件配置。Webhook 地址、密码、签名和刷新令牌不写入数据库错误日志，接收端原始错误文本也不返回调用者。

验证入口：现有通知配置页面、通知渠道 API 和 src/notification-credentials.mysql.test.ts。真实验收显式注入 NOTIFICATION_CREDENTIALS_MYSQL_JSON，测试创建随机独占 schema；可用 NOTIFICATION_CREDENTIALS_EVIDENCE_DIR 保存审计摘要与三个桌面尺寸截图。默认测试不读取本机认证文件、不连接共享业务库。HTTP 接收器与 SMTP 为隔离协议端点，DNS 及 HTTPS 目的地受控，不代表厂商生产账户、真实 TLS 或整服部署验证。
