## 2. F1：第一条业务 DML 前的准确 FK 语义拒绝

`ForeignKeyShape` 原来只记录列、引用表名与引用列名，`REFERENCED_TABLE_SCHEMA` 与
`REFERENTIAL_CONSTRAINTS.UPDATE_RULE/DELETE_RULE` 完全没有读取，导致两条真实反例能穿过 `verifyLiveFixture`
并执行真实 DML。补修：

- `readSchemaStructure` 由 `KEY_COLUMN_USAGE` 联接 `REFERENTIAL_CONSTRAINTS`（schema+约束名+表名），
  读取每个外键的 `REFERENCED_TABLE_SCHEMA`、`REFERENCED_TABLE_NAME`、引用列序、`UPDATE_RULE`、`DELETE_RULE`。
- 冻结结构用 `$self` 占位表示“本 schema”，`diffFrozenStructure(actual, expected, schema)` 按被测 schema
  解析后比较；跨 schema 的同名表（同表名、同列名、不同 `REFERENCED_TABLE_SCHEMA`）因此不再被当作同一对象。
- 比较项为 列序 → 引用 schema → 引用表 → 引用列 → `ON UPDATE` → `ON DELETE`；差异信息写入
  `structure-drift` 的 `detail.diffs`。`seed`/`up`/`down` 三个写入口仍在第一条业务 DML 前调用该预检，
  `plan` 仍零连接零写。

### 2.1 Chief 两条真实反例（同一独占 fixture 内真实 DDL）

| 真实边界 | 构造后的实际 `information_schema` | seed / up / down | 结果 |
|---|---|---|---|
| candidate `fk_draft_template` 跨库引用 `max237_t2b_d1.metric_templates_v2` | `referenced_schema=max237_t2b_d1`，`NO ACTION/NO ACTION` | 三个入口均 `structure-drift`，业务 DML 0 | **PASS**（base 为 `accepted` 并写入 2/2/2/3/2 条） |
| 同库 FK 改为 `ON DELETE CASCADE` | `referenced_schema=max237_t2b`，`NO ACTION/CASCADE` | 三个入口均 `structure-drift`，业务 DML 0 | **PASS**（base 为 `accepted` 并写入 2/2/2/3/2 条） |

两次拒绝前后三库完整 manifest（含空表与行内容）逐条相等；DDL 恢复后候选结构快照与构造前逐字节相等，并
重新通过 `verifyLiveFixture`。业务 DML 由连接级代理统计 `INSERT/UPDATE/DELETE/REPLACE`，两例六个入口均为 0。
真实 DDL 只在本 run 自建 fixture 内以 root 构造，原 140/候选 DDL 文件未改，不声称 DDL 可事务回滚。

### 2.2 合成矩阵（明确标注 synthetic）

对 source/candidate/restore 三个真实结构快照中的全部四个外键（`fk_draft_template`、`fk_ti_template`、
`fk_tiv_item`、`fk_tv_template`），逐一注入 7 类变异：跨 schema 引用、引用表、引用列、`ON UPDATE CASCADE`、
`ON UPDATE SET NULL`、`ON DELETE CASCADE`、`ON DELETE SET NULL`。**84/84** 变异均被
`diffFrozenStructure` 捕获（3 schema × 4 FK × 7 = 84）。该矩阵证明比较器本身，真实 MySQL 语义由 2.1 与
每次写入口的冻结预检证明。

## 3. F2：拒绝场景与安全 roundtrip 独立

`drill.ts` 现在必须显式选择场景，且两个场景各用一具 **fresh fixture**：

`--scenario reject`（fixture A，14/14 PASS）：
plan/guards → 合成矩阵 → 身份拒绝 → 两条真实 FK 漂移 → source 结构漂移 → seed → candidate 结构漂移 →
真实 up → 通过 adapter 写入合法超界行（actor `2147483648`/`9007199254740991`、canonical 512 字符、
semver 100 字符、年份 `0000`）→ `down` 以 `down-irreversible` 拒绝。拒绝后保存三库完整 manifest 与保留行，
超界原因逐条记录（`exceeds INT`、`not VARCHAR(128)`、`not VARCHAR(16)`、`precedes DATETIME year 1000`），
**不删除任何合法新数据**；该 fixture 连同超界行一起由 `env-clean.sh` 按准确 ID 整体销毁。

`--scenario safe`（fixture B，27/27 PASS）：
plan/guards → seed（仅安全旧数据）→ 已接受的 R1 事务故障注入 → 真实 up → adapter 读回（PK、revision、
pointer、SQL NULL、JSON 原值、瞬时）→ 关闭并以新 pool 重读 → 幂等 no-op / 目标漂移拒绝 → restore 结构
漂移拒绝 → down 事务故障 → 安全 down → 幂等 no-op → 两连接最终三库 manifest。down 结果为
restore manifest = source manifest，candidate 仍保留 up 副本。

禁止的旧路径（先 `DELETE` 超界行再对同一 candidate 做 down 冒充回退）已从 drill 删除；`t2b-drill.json`
仍是 base `6dcb16651` 的 TX-GUARD 历史记录，不再是当前 drill 的证据。
