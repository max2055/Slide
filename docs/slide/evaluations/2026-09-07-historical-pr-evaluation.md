## 2. 评估对象与判断尺度

产品范围采用用户最新定位：数据库是重点，服务器有独立运维价值并能支撑数据库诊断，网络设备保持有限能力。服务器故障不要求必须影响某个数据库才能进入处理流程。

本报告比较三个范围，以免把所有可能新增的功能都算成原方案的功劳：

| 范围 | 内容 | 覆盖含义 |
| --- | --- | --- |
| A：现有能力 | 已落地的资源关系、质量/过期字段、权限、审批、幂等、状态机、测试门禁 | 用作增量评估基线，不能重复算作改造收益 |
| B：拟议核心方案 | 联合证据、可执行不变量、可追溯决策、操作契约、独立结果验证、经验反馈 | 主要覆盖被纳管资源及其采集和操作链路 |
| C：必要补充 | Slide 自身运行观测、浏览器真实路径探测、部署/升级验证与发布信息 | 使平台自身、UI、容器和迁移问题成为可检测信号；属于显式新增范围 |

能力分别评估，不把“看到错误”等同于“修复错误”：

| 能力 | 成功的具体含义 |
| --- | --- |
| 发现 | 在预算时间内报告正确的异常/不变量违例，并引用触发时存在的证据 |
| 定位 | 区分合理竞争假设，证据不足时保留未知，指出下一项可区分根因的检查 |
| 预防/限制影响 | 由执行层拒绝非法状态转换、过期证据、跨范围操作或重复副作用 |
| 运行恢复 | 使用预先授权且已验证的动作恢复服务，再通过独立探测确认结果 |
| 永久修复 | 修改程序、SQL、适配器、部署配置或产品规则，通过研发测试并发布 |

下面的“可”均表示有明确机制的预期能力，仍需实测。读懂日志、拥有 `confidence` 字段、存在状态机名称，均不是已经通过回归的证据。永久修复还需要单独的研发执行环境与发布权限。

### 3.1 按架构能力归纳

能被拟议核心闭环直接覆盖的主要是运行资源和 Agent 控制类问题：#5、#6、#7、#9、#11、#12、#13、#14 的采集/会话部分、#15、#18/#19、#23、#24、#25、#27、#28、#31。它们共同要求“有证据才判断、有权限才行动、动作后重新验证”。

无论新架构如何建设，都不能直接“解决”的是底层永久缺陷本身：Oracle/DM8 方言、适配器字段口径、CSP/监听配置、迁移兼容列表、Logo/导航代码、依赖版本和卷权限修复。架构可以更早发现、阻断错误操作、给出证据和进入研发修复流程；完成永久修复仍需对应代码、配置或部署变更。

## 4. 当前基础与新增验收的区别

现有 [资源模型](../../../apps/db-ops-api/src/resources/types.ts) 已有三类资源、关系来源与生效时间，以及观察值质量和有效期。现有 [分析结构](../../../apps/db-ops-api/src/analysis/analysis-envelope.ts) 已有假设、证据引用、建议和置信度。因此增量工作应考察这些语义在采集、存储、API、Agent 和页面全链路是否成立。

有三处会直接影响本次评估口径：

1. [分析完成保存](../../../apps/db-ops-api/src/ai-analysis-database-service.ts) 的 `completeAnalysisEnvelope` 先校验 envelope 结构，再保存结果。这个路径没有按冻结证据快照逐条验证 `evidenceRefs` 的存在和陈述支持关系。新验收需要检查引用能解析、时间/资源匹配，以及结论有无越过证据。
2. [事件恢复验证](../../../apps/db-ops-api/src/alert-event-service.ts) 的 `verifyRecovery` 记录时间、操作者与理由；`closeEvent` 据此允许关闭。这能实现人工确认门禁，尚不等于自动执行独立健康探测或验证持续恢复窗口。人工确认和自动验证应保留不同来源。
3. [qualification 映射](../../../tests/qualification/coverage-matrix.ts) 明确说明自己是索引而非发布决策，主要检查 finding ID 映射与文件存在。映射完整性、原缺陷复现、新架构检出和恢复验证必须分开记录。

这些是评估设计所需的能力区别，不将其扩展为本轮代码修复。

## 5. 历史回放方法是否合理

合理，适合作为架构的第一套经验性基准。它能让每项抽象能力对应真实问题、明确验收和投入优先级。现阶段只有静态反事实分析：推断新机制在旧场景中可能改变什么。只有运行可重复的故障案例后，才构成可执行的回归评估。

需要控制以下偏差：

- PR 是交付容器，不是样本单位。综合 PR 包含多类问题，小 PR 可能只是同一问题的一次后续修复。按故障机制拆分，按关联故障族分组；不以“覆盖多少 PR”推导准确率。
- PR 修复说明不等于生产事故记录。来源区分生产报告、评审发现、测试发现、功能需求、政策调整，以及尚未确认的现场描述。不能推断发生频率、事故时长或 MTTR。
- 防止答案泄漏。故障发生时可用的指标、日志、配置、版本、权限是被测 Agent 的输入；修复 PR、最终诊断、修复后代码、测试答案和相关 Git 历史留给评估器。研发 Agent 实验允许读源码时，也要明确限定版本和可见范围。
- 防止重复计功。已在当前 A 中落地的幂等、过期处理、权限检查，不再作为 B 的新增覆盖。比较同一模型、可行动权限和预算下的增量。
- 防止同源错误自证。展示值、健康分和报告若都来自同一个错误采集公式，它们互相一致仍可能全错。必须检查原始来源、计算口径/单位/版本，必要时采用独立读回。
- 防止评估集过拟合。按故障族划分开发集与留出集；同源重复案例不能分别进入训练与测试后被当成泛化。另加相同症状不同根因、单故障变复合故障和合法正常状态的变体。
- 模拟不能代替实际协议与部署验证。单元或源码字符串断言可验证局部契约，不能证明 Oracle 11g/DM8 查询、真实 SNMP/SSH、Nginx WebSocket 或旧 Docker 卷行为。
- 历史样本不能穷尽未来风险。历史集外仍需按能力契约覆盖未知版本、权限变化、部分故障和长期资源泄漏等场景，覆盖范围单独说明。

## 6. 可执行评估设计

### 6.1 一条历史问题的样本契约

每个案例记录 `caseId`、来源 PR/提交、来源类型、故障族、修复前/后 SHA、环境和适配器版本、触发条件、故障注入方式、时间轴、故障前正常状态、证据可见范围、合法动作、禁止动作、预期检测/恢复时限、独立验证器和不确定项。

结果分别保存 `detected`、`localized`、`contained`、`recovered`、`permanentFixRequired`、证据引用、时间、动作副作用、实际资源消耗。证据不可重建时标注 `not_replayable_yet`，不能猜测原始日志或默认算通过。

### 6.2 执行次序

1. 校准案例：在隔离测试环境确认修复前版本可复现失败，修复后版本满足原修复断言。大型 PR 优先拆成小型故障注入或最小契约样本，不把整仓历史回退当作唯一复现方式。
2. 冻结案例：评估器持有故障真值、修复证据和结果断言；被测 Agent 只读决策时可得的材料。训练/开发案例和留出案例固定版本。
3. 对照 A/B/C：在相同触发、负载、外部故障与权限预算下比较现有机制、拟议核心机制、核心加新增探针。架构自身增加的信号按实验组记录；不允许仅给新组额外提供答案或已修复业务逻辑。
4. 防止错误归因：如果移植新架构顺便修了原业务 bug，单列这项修复。要比较架构机制，应在共同边界注入同等故障，检验何时发现、是否隔离、如何恢复。
5. 分层验证：确定性单元/契约用例验证状态和数据语义；隔离服务集成验证并发、协议、持久化；真实构建浏览器和容器升级验证用户路径；然后才运行有随机性的 Agent 决策评估。
6. 独立验收：动作执行器的返回值只表示动作结果。由新采样、实际连接、持久化记录和副作用计数确认恢复；结果不明保持 unknown，不宣称 exactly-once，也不自动重放危险动作。
7. 重复与预算：Agent 实验记录模型、提示词、工具和策略版本，运行多次观察稳定性；工具次数、运行时间、模型吞吐与费用预算相同。超预算、超时、缺证据分别计分。

这不会以“当前所有测试通过”代替历史重放。当前代码已经含有修复，仅跑当前测试无法证明新架构曾经能发现旧问题。

### 6.3 计分

- 检出率：成功检出的可执行故障样本 / 同范围全部可执行故障样本。
- 误报率：正常对照被错误升级的次数 / 正常对照次数；特别纳入停用采集、维护窗口、合法鉴权拒绝和 unsupported 指标。
- 定位正确率：评估器认可的根因或有证据支持的候选集比例；正确保留未知单独统计。
- 证据有效率：引用存在、资源匹配、时间有效、陈述被支持的比例；来源不可核实不得因模型高置信度而通过。
- 防护有效性：该拒绝的动作是否在副作用发生前被阻断，并统计合法动作被误阻断的比例。
- 运行恢复率：已授权、具备恢复动作的案例中，通过独立恢复断言的比例；同时公布不可自动恢复案例的数量及原因。
- 时间与成本：故障到检出、首个正确候选、持续恢复分别计时；记录每案例真实 input/output、cached input、工具成本。总吞吐按 input + output，cached input 不重复相加。
- 稳定性：多次运行的成功率和范围，避免仅展示最好的一次。受控实验中的恢复时间不直接宣称为生产 MTTR 改善。

本轮不提供检出率、自动修复率或 MTTR 改善百分比，因为尚未执行上述实验。

## 7. 建设优先级与首批案例

优先级按历史故障机制和可验证程度判断，不代表真实故障频率统计：

1. P0：补齐采集语义。每指标保留成功/失败时间、来源、单位、维度、统计口径和适配器版本；采集尝试与成功持久化分开；失效数据不能继续作为当前健康依据。
2. P0：让 Slide 自身可被观察。记录浏览器到代理入口的 WebSocket 生命周期、run/operation/approval 状态，增加从真实入口经过 Nginx 的合成探测；应用无法启动时由独立于应用进程的探针记录原因。
3. P0：在现有执行点强化不变量和恢复确认。以已有权限、幂等、状态机为基础；判断必须在发生副作用的边界执行，验证必须读到动作后的真实结果。
4. P1：补齐部署和升级证据。记录 release SHA、迁移账本、运行 UID、挂载权限、监听配置与能力测试结果；测试已有卷/已有数据库升级，不只测空环境安装。
5. P1：加入用户路径断言。覆盖三类资源的入口、手机端操作、主题在生产 CSP 下的恢复、鉴权和聊天确认。通过统一证据接口提供探针结果，不必为每类探针单建页面。
6. P2：再扩展关联诊断、预期模型和经验检索。历史里大量问题是确定性契约或状态错误，简单断言足以发现；统计异常模型主要补充性能偏移，不能代替单位/权限/状态规则。

首批建议将以下案例做成可执行种子；它们是设计，不是本轮已运行测试：

| 案例 | 历史来源 | 故障注入/前置状态 | 独立验收与合法动作 |

| R01 凭据补录后不采集 | #9、#14 | 先缺凭据，后保存有效凭据，运行时仍无连接 | 在契约约定的采集期限内重建连接并产生新持久化样本；已有凭据不可解密时明确要求凭据修正，不盲目重试 |

| R04 Oracle 查询兼容与超时 | #12 | 11g 语法限制或查询不返回 | 有界终止并释放/恢复连接设置；缺数据保留未知。永久修复 SQL 要通过对应版本集成测试 |

先实现 R01、R02、R06、R08、R10 和 R12，覆盖采集、状态、审批、部署、页面五类机制；R04/R05 的真实数据库版本环境另列前置条件。每一类都必须有正常对照，例如停用采集不算故障、撤销登录不应自动恢复访问、不支持的网络 OID 不应生成“0 且健康”。

对暂不可自动恢复的案例，合格输出可以是“引用证据并提交研发修复/人工处理”，但这只计入发现与定位，不计入运行恢复。
